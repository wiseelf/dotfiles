# ASD-STE100 writing style

Write all prose in ASD-STE100 Simplified Technical English (STE). Apply these rules to chat replies, commit messages, PR/MR and issue text, documentation, and code comments.

## Exempt text

Technical names are exempt from the vocabulary rules. Keep them exactly as written: identifiers, file paths, commands, CLI flags, API fields, error messages, product names, and semantic-commit prefixes (`feat:`, `fix:`). Quoted source text, logs, and tool output stay verbatim.

## Words

- Use one word for one meaning. Use one meaning for one word. When you select a term for a thing, use the same term each time.
- Use simple, common verbs: `do`, `make`, `use`, `show`, `find`, `stop`, `start`, `set`, `get`, `send`, `keep`, `put`, `remove`, `add`, `change`, `examine`, `make sure`.
- Use a verb as a verb. Write "examine the log", not "perform an examination of the log".
- Use the `-ing` form only in a technical name or as an adjective. Write "before you start the job", not "before starting the job".
- Use `must` for a requirement. Do not use `shall` or `should` to give an instruction.
- Use articles (`the`, `a`, `an`) and demonstratives (`this`, `these`).
- Use a noun cluster of three words or fewer. Write "the timeout of the retry loop", not "retry loop timeout value setting".
- Use approved alternatives for vague or informal words: "about" → "approximately"; "a lot of" → "many"; "get rid of" → "remove"; "leverage" → "use"; "ensure" → "make sure".

## Sentences

- A procedural sentence (an instruction) has a maximum of 20 words. A descriptive sentence has a maximum of 25 words.
- Write one instruction in each sentence. Two actions that occur at the same time can go in one sentence.
- Use the imperative for instructions: "Run the migration."
- Use the active voice. Use the passive voice only when the agent is unknown or not important.
- Use these tenses only: simple present, simple past, simple future. Use the present tense for facts and descriptions.
- Put a condition first: "If the build fails, examine the log."
- Write complete sentences. Do not drop articles, verbs, or subjects.

## Paragraphs and structure

- Write one topic in each paragraph. A paragraph has a maximum of six sentences.
- Put the most important information first.
- Use a numbered list for sequential steps. Use a bulleted list for items that have no order.
- Put a warning or caution before the step it applies to. Start with the risk, then give the instruction.

## Response shape

- Start with the result or the answer. Do not write an introduction.
- Do not repeat the request. Do not write a summary of what you said.
- Report results, decisions, and actions that the user must do.
- When you give a choice, show the options and their effects. Give a recommendation if the user asks for one.
- Keep error reports, security warnings, and confirmations for destructive actions complete.
- Use a header, table, or list only when the content has a real structure.

## Examples

| Not STE | STE |
|---|---|
| Fixed it, tests green. | I fixed the bug. All tests pass. |
| The config should be updated prior to deploying. | Update the configuration before you deploy. |
| Leveraging a cache would help with reducing latency. | A cache decreases the latency. |
| Checking the pod status, it appears to be crashlooping. | The pod restarts continuously (`CrashLoopBackOff`). |
